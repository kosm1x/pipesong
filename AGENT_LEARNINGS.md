# Agent Learnings — pipesong

## Standing rules
- Before paying for a GPU gate on a new STT/TTS model, run the cheapest gate that can kill it: offline CPU WER on `benchmarks/audio/samples/phone_*.wav` bounds streaming WER from above.
- Treat a pass on the 100 synthetic phone clips as necessary, not sufficient. Clean TTS voices flatter every engine, so real es-MX telephony audio decides.
- Normalize numbers (digits vs spelled-out) before scoring Spanish WER. Otherwise formatting dominates the error count.
- Count usted→tú register flips as their own metric. For a formal agent a flip changes meaning; a dropped accent does not.
- Flux does STT, end-of-turn detection and barge-in (`src/pipesong/pipeline.py:90`). Any STT swap must also bring back turn detection (Silero VAD + Smart-Turn), so price that into the integration cost.
- Read a model's license for how it treats OUTPUTS, not just commercial thresholds. NetEase's R2T2 license counts transcripts as derivative works that must not improve another commercial model.

- Read the INSTALLED package before writing against a remembered API (pipecat `_handle_bot_speech`, mcp 2.x `MCPServer`, kokoro-onnx already shipped by `pipecat-ai[kokoro]`): `ls .venv/lib/python3.12/site-packages/<pkg>` first. Seen on A.0 and B.1.
- Any frame injected into the Pipecat pipeline is defined by its POSITION: audio at the head is STT input; TTS-shaped frames before `TTSService` are re-synthesized or overtake queued audio. State where it enters and prove it with the real `create_pipeline` order test + a fake-STT/real-chain test, never a hand-built pipeline alone. Seen on A.0 and A.1.
- A green suite from the implementer is not the gate: every bundle so far had one critical only a qa-auditor round with mutants found (STT leak, question/statement key collision, credential scope). Run R1→R2(→R3) scoped to "what changed".
- A gate metric must span two REAL events (user EOT → bot first audio) and have a test where it can come out high; a number computed between two in-process calls cannot fail.

## 2026-09-23 — Confucius4-R2T2 streaming-ASR probe (gate 1)
- **Avoid:** trusting the roadmap's "local faster-whisper fallback" as a live slot. It exists only in `benchmarks/scripts/stt_validation.py` and is not wired into the pipeline → grep `src/pipesong/` for a fallback before calling a candidate a "drop-in".
- **Mistake:** ran the first probe as a session-bound background task and lost it on disconnect → run any job longer than a few minutes under `systemd-run --unit <name>`, resumable (one JSON line per clip), from the start.
- **Avoid:** reading raw WER as recognition quality. 14 of R2T2's 20 wrong clips and 20 of whisper's 23 differed only by number format → normalize numbers, then read the residual errors class by class.
- **Better:** write the kill rule down before running (KILL if more than 1 pt worse than whisper-turbo, or above 10 %), then apply it verbatim. R2T2 scored 4.66 % vs 6.76 %, so it passed. Results: `docs/PROBE-R2T2-2026-09-23.md`.

## 2026-10-13 — A.0 pre-recorded disclosure
- **Avoid:** queuing a plain `OutputAudioRawFrame` for bot speech. Pipecat 1.7's output transport only emits `Bot{Started,Stopped}SpeakingFrame` for `TTSAudioRawFrame`/`SpeechOutputAudioRawFrame` (`transports/base_output.py` `_handle_bot_speech`), so the first-bot-complete unmute and `DisclosureGate` would never fire → read `_handle_bot_speech` before injecting audio.
- **Better:** follow injected `TTSAudioRawFrame` audio with a `TTSStoppedFrame`; without it the bot turn only ends at the transport's 3 s idle fallback (`BOT_VAD_STOP_FALLBACK_SECS`). `tests/test_disclosure_clip.py` pins both behaviours, so a pipecat upgrade that changes them fails loudly.
- **Better:** check what the live service already ships before adding a dependency. Pipecat's `KokoroTTSService` runs on kokoro-onnx (installed via `pipecat-ai[kokoro]`); the roadmap's `kokoro` package would have added 22 packages (spacy et al.) for a second engine that differs from the one callers hear.
- **Mistake:** queued the clip (an output audio frame) at the pipeline head. Every `AudioRawFrame` is STT input (`services/stt_service.py` `process_frame`), so Flux would have transcribed the bot's own disclosure as user speech; QA caught it. Fix: `DisclosureClipPlayer` swaps the disclosure `TTSSpeakFrame` for the clip right before TTS → the check is BOTH a pipeline test with a fake STT recording `run_stt` bytes AND an order assertion on the real `create_pipeline` output (`tests/test_pipeline_order.py`); a hand-built test pipeline does not pin the real order, and a transport-only test catches neither.
- **Mistake:** the first pytest run died at collection: nltk's CWD-import guard blocks pipecat's deps from the in-repo `.venv` unless `pipesong` (which sets `NLTK_DISABLE_IMPORT_SECURITY`) is imported first → `tests/conftest.py` imports `pipesong` before any test module touches pipecat.

## 2026-10-13 — A.1 phrase corpus + mixer
- **Avoid:** injecting TTS-shaped frames upstream of a pipecat 1.7 `TTSService`. It consumes every `TextFrame` (a `TTSTextFrame` from upstream is synthesized a second time), and a `skip_tts` text frame is pushed immediately, overtaking the previous sentence's queued audio, so the context gets clauses out of order (both proven with real Kokoro) → route the hit as a non-text `DataFrame` marker, which `TTSService.process_frame` puts on its `_serialization_queue` in arrival order, and expand it right after TTS (`PreRecordedClipEmitter`).
- **Better:** prove "behaves like TTS" by running the same LLM response through the real chain (SpanishOnlyFilter → SentenceStreamBuffer → mixer → KokoroTTSService → emitter → `BaseOutputTransport` → `LLMAssistantAggregator`) with and without a corpus and asserting equal context messages; the X3/X4 mutants (direct push, marker as `SystemFrame`) both go RED there and nowhere cheaper.
- **Avoid:** corpus lines with commas for LLM output. `SpanishOnlyFilter` turns commas into periods and `SentenceStreamBuffer` splits there, so "Un momento, por favor." reaches the mixer as two frames → one clause per line; the generator prints a note for multi-clause lines (they can still match whole `TTSSpeakFrame`s such as tool fillers).
- **Mistake:** a 0.1 s test clip produced no `BotStartedSpeakingFrame` on the 8 kHz test transport (the stream resampler's delay swallowed it) and looked like a mixer bug → test clips at least 0.2 s, as the A.0 tests already used.
- **Mistake:** made corpus matching punctuation-insensitive, which also erased sentence type: "¿Su cita ha quedado confirmada?" keyed to the "Su cita ha quedado confirmada." clip (QA W1) → keep a `?`/`!` token in the key; the check is a test asserting question vs statement vs exclamation of the same words give three different keys.
- **Mistake:** reported a corpus hit's TTFB as the emitter's marker-receipt → audio-push interval: two in-process `push_frame` calls, ~0 ms by construction, so "TTFA P50 < 200 ms on hit turns" could never fail (QA round 2) → measure between the two real events, user end of turn (`UserStoppedSpeakingFrame`) and the bot's first audio (`BotStartedSpeakingFrame` upstream from the output transport): `MetricsCollector.ttfa_ms`. Also: `MetricsFrame` is a `SystemFrame` and overtakes queued control frames (`LLMFullResponse*Frame`), so a burst-sent test lies; pace test frames like the live gaps.

## 2026-10-13 — B.1 MCP server
- **Avoid:** following "use `mcp.server.fastmcp.FastMCP`" on the SDK we install. mcp 2.x renamed it `mcp.server.mcpserver.MCPServer`; `mcp.server.fastmcp` is a stub that raises → read the installed package (`ls .venv/.../mcp/server`) before writing against a remembered API.
- **Avoid:** raising a plain exception from an `MCPServer` tool. Anything that is not a `ToolError` reaches the caller as only "Error executing tool <name>", so an API's status and 422 body would vanish → `PipesongAPIError` subclasses `ToolError`; the check is an in-memory `Client(mcp)` call asserting the HTTP status is in the error text (mutant with an `Exception` base goes RED).
- **Better:** pin an API wrapper to the real routes by matching each recorded request with `route.matches(scope) == Match.FULL` on `pipesong.main.app`. FastAPI 0.141 wraps included routers in `_IncludedRouter` (no `.path`), so walking `route.path` fails; `matches` is method-aware (a wrong method is only PARTIAL).
- **Avoid:** mirroring every field of a request model into a tool without checking each is consumed. `OutboundCallCreate.variables` is accepted and silently dropped by `api/outbound.py`, so `call_start` leaves it out → grep each field's use before exposing it.
- **Mistake:** the MCP client first read its URL and key from the app's `BaseSettings`, whose `env_file=".env"` is relative to the process cwd. An MCP client launched from another project would have loaded THAT project's `.env`, sent its generic `API_KEY` as a Bearer token to the default `:8080` (mission-control on this VPS), and any unknown key in that `.env` aborted the import with `extra_forbidden` (QA C1/C2) → MCP/CLI entrypoints read namespaced env vars (`PIPESONG_API_URL`, `PIPESONG_API_KEY`) from `os.environ` only, with no default URL; the check is a subprocess test run from a scratch cwd that holds a foreign `.env`.
